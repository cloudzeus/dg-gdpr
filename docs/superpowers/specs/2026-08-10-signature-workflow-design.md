# Στάδιο 3 — Κύκλωμα Υπογραφής και Κλείσιμο Έργου — Design Spec

**Ημερομηνία:** 2026-08-10
**Project:** dg-gdpr (GDPR Compliance OS)

## Σκοπός

Το Στάδιο 2 παράγει τα έγγραφα σε `DRAFT`. Αυτό το στάδιο τα στέλνει, παρακολουθεί ποιος υπέγραψε, υπενθυμίζει, και κλείνει το έργο όταν όλα είναι εντάξει.

Είναι το τελευταίο κομμάτι του αρχικού οράματος: *«θα έκανε auto generate όλα τα docs που πρέπει να υπογραφούν και θα ολοκλήρωνε το έργο»*.

## Πώς υπογράφεται

**Δύο δρόμοι, ένας σύνδεσμος.** Στέλνουμε email με μοναδικό token. Ο αντισυμβαλλόμενος ανοίγει μια δημόσια σελίδα, βλέπει το έγγραφο, και επιλέγει:

- **Ηλεκτρονική επιβεβαίωση** — δηλώνει ονοματεπώνυμο και ιδιότητα, τσεκάρει ότι δεσμεύει νόμιμα την εταιρία, πατάει υπογραφή. Καταγράφονται χρόνος, IP, user-agent και το κείμενο που είδε.
- **Ανέβασμα υπογεγραμμένου** — αν προτιμά χαρτί ή ψηφιακή υπογραφή τρίτου, ανεβάζει το PDF.

Η ηλεκτρονική επιβεβαίωση είναι **απλή ηλεκτρονική υπογραφή** κατά eIDAS. Δεν είναι εγκεκριμένη, και δεν πρέπει να παρουσιάζεται ως τέτοια. Για σύμβαση άρθρου 28 μεταξύ επιχειρήσεων είναι αποδεκτή, και το αρχείο ελέγχου είναι αυτό που της δίνει βάρος — γι' αυτό καταγράφεται πλήρες.

Η υποδομή υπάρχει ήδη από τις συναινέσεις: `generateConsentToken`, `getClientIp`, `sendMail` μέσω Mailgun, και το μοτίβο δημόσιας σελίδας με token στο `/(public)/c/[layout]/[slug]`.

## Μοντέλο δεδομένων

Ένα νέο μοντέλο. Οι υπάρχουσες `DpaContract.signedAt` / `signedDocUrl` / `status` **μένουν** ως η τελική κατάσταση· το νέο μοντέλο κρατά τη διαδρομή προς αυτήν.

```prisma
model SignatureRequest {
  id            String            @id @default(cuid())
  projectId     String
  /** Τι υπογράφεται. Πολυμορφικό: DpaContract, DpiaReport, ContractClauses. */
  entityType    String
  entityId      String
  documentUrl   String

  /** Ποιος υπογράφει. */
  recipientName  String
  recipientEmail String
  companyId      String?

  token         String            @unique
  status        SignatureStatus   @default(PENDING)
  expiresAt     DateTime

  sentAt        DateTime?
  viewedAt      DateTime?
  signedAt      DateTime?
  declinedAt    DateTime?
  declineReason String?           @db.Text

  /** Τι δήλωσε ο υπογράφων — το βάρος της απλής ηλεκτρονικής υπογραφής. */
  signerName    String?
  signerTitle   String?
  signerIp      String?
  signerAgent   String?           @db.Text
  /** Το ανεβασμένο υπογεγραμμένο, όταν επιλεγεί αυτός ο δρόμος. */
  uploadedUrl   String?

  reminderCount Int               @default(0)
  lastReminder  DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  project Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  company Company? @relation(fields: [companyId], references: [id])

  @@index([projectId])
  @@index([status, expiresAt])
}

enum SignatureStatus { PENDING SENT VIEWED SIGNED DECLINED EXPIRED }
```

**Γιατί πολυμορφικό `entityType`/`entityId`** και όχι ξεχωριστές σχέσεις: υπογράφονται τρεις διαφορετικοί τύποι και θα προστεθούν κι άλλοι. Το ίδιο μοτίβο χρησιμοποιεί ήδη το `AuditLog` και το `IntakeGap.createdEntityType`.

## Ασφάλεια του συνδέσμου

Ο σύνδεσμος φτάνει σε τρίτον, εκτός του συστήματος. Τέσσερις κανόνες:

1. **Το token είναι το μόνο διαπιστευτήριο** — τυχαίο, 32 bytes, μοναδικό. Καμία απαρίθμηση: άγνωστο ή ληγμένο token δίνει την ίδια απάντηση με έγκυρο-αλλά-υπογεγραμμένο, ώστε να μη μαθαίνει κανείς τι υπάρχει.
2. **Λήγει.** Προεπιλογή 30 ημέρες, ρυθμιζόμενη. Ληγμένο token δεν υπογράφει· ζητά νέα αποστολή.
3. **Μία χρήση για υπογραφή.** Μετά την υπογραφή η σελίδα δείχνει την επιβεβαίωση, δεν επιτρέπει δεύτερη.
4. **Καμία πρόσβαση σε άλλα δεδομένα.** Η δημόσια σελίδα δείχνει ΜΟΝΟ το έγγραφο και τα μέρη του — ούτε κενά συμμόρφωσης, ούτε το προφίλ, ούτε άλλα έργα.

Η σελίδα ζει στο `(public)` group, εκτός `(app)`, ώστε να μην περνά από το auth layout.

## Δικλείδα αποστολής: τίποτα δεν φεύγει κατά λάθος

Τα email αυτού του σταδίου πάνε σε **πραγματικούς πελάτες**, και μια λάθος αποστολή δεν ανακαλείται. Η προσοχή δεν αρκεί ως εγγύηση· χρειάζεται μηχανισμός.

**`SIGNATURE_TEST_RECIPIENT`** — όταν είναι ορισμένη, **κάθε** email υπογραφής πάει σε αυτή τη διεύθυνση, ανεξάρτητα από τον πραγματικό παραλήπτη. Το σώμα του μηνύματος ξεκινά με ορατή προειδοποίηση:

> ⚠ **ΔΟΚΙΜΑΣΤΙΚΗ ΑΠΟΣΤΟΛΗ** — το κανονικό μήνυμα θα πήγαινε στον/στην «Δημήτριος Κολλέρης» <d.kolleris@example.gr>.

Ο σύνδεσμος και το token είναι πραγματικά, ώστε η ροή να δοκιμάζεται πλήρως. Μόνο ο παραλήπτης αλλάζει.

Τρεις κανόνες γύρω από αυτό:

1. **Η μεταβλητή είναι ορισμένη μέχρι να αποφασιστεί ρητά το αντίθετο.** Δεν είναι opt-in για δοκιμές· είναι opt-out για παραγωγή.
2. **Το UI το δείχνει.** Όταν η ανακατεύθυνση είναι ενεργή, το κουμπί αποστολής λέει «Αποστολή (δοκιμαστικά σε …)» αντί για σκέτο «Αποστολή». Ένας μηχανισμός ασφαλείας που δεν φαίνεται είναι μηχανισμός που κάποιος θα ξεχάσει ότι υπάρχει — προς τη μία ή την άλλη κατεύθυνση.
3. **Καταγράφεται στο `AuditLog`** ποιος ήταν ο πραγματικός παραλήπτης και πού στάλθηκε τελικά.

Χωρίς τη μεταβλητή, τα μηνύματα πάνε κανονικά. Η αφαίρεσή της είναι συνειδητή απόφαση παραγωγής, όχι παράλειψη ρύθμισης.

## Υπενθυμίσεις

Το υπάρχον `api/cron` τρέχει ήδη προγραμματισμένες εργασίες. Προστίθεται μία: αιτήματα σε `SENT` ή `VIEWED` που έχουν μείνει **7 ημέρες** χωρίς απάντηση παίρνουν υπενθύμιση, **έως τρεις φορές**. Μετά σταματά — ένα σύστημα που στέλνει επ' άπειρον email είναι ενοχλητικό, και ένας αντισυμβαλλόμενος που αγνόησε τρεις υπενθυμίσεις χρειάζεται τηλέφωνο, όχι τέταρτο email.

Όσα περνούν το `expiresAt` γίνονται `EXPIRED` από την ίδια εργασία.

## Κλείσιμο έργου

Το έργο γίνεται `COMPLETED` όταν **και τα δύο** ισχύουν:

- Κάθε `SignatureRequest` του έργου είναι `SIGNED`
- Κάθε `IntakeGap` με σοβαρότητα `CRITICAL` είναι `RESOLVED`

Αυτό είναι αυστηρότερο από τον κανόνα του commit, και σκόπιμα: στο commit αρκούσε να υπάρχει προτεινόμενη κάλυψη, γιατί το σύστημα επρόκειτο να την εκτελέσει. Εδώ πρέπει να έχει όντως εκτελεστεί και υπογραφεί.

Ο έλεγχος είναι **καθαρή συνάρτηση** `canCompleteProject(signatures, gaps)` που επιστρέφει `{ allowed, reasons[] }`, όπως το `canCommit`. Το UI τυπώνει τους λόγους αυτούσιους.

Ένα `DECLINED` αίτημα δεν μπλοκάρει σιωπηλά — εμφανίζεται με τον λόγο άρνησης, και ο χρήστης είτε στέλνει νέα εκδοχή είτε το ακυρώνει ρητά.

## Τι ΔΕΝ κάνει

**Δεν είναι εγκεκριμένη ηλεκτρονική υπογραφή.** Αν χρειαστεί ποτέ, ο δρόμος είναι πάροχος τύπου DocuSign· η δομή `SignatureRequest` τον δέχεται χωρίς αλλαγή, με ένα ακόμη πεδίο για το εξωτερικό envelope id.

**Δεν στέλνει χωρίς έγκριση.** Κάθε αποστολή είναι ρητή ενέργεια του χρήστη σε συγκεκριμένο παραλήπτη. Δεν υπάρχει «στείλε τα όλα» που να φεύγει μόνο του — τα email πάνε σε πελάτες, και μια λάθος μαζική αποστολή δεν παίρνεται πίσω.

## Κριτήρια επιτυχίας

- Από παραγόμενο DPA, ένα κλικ στέλνει email με σύνδεσμο στον σωστό παραλήπτη
- Ο σύνδεσμος δείχνει το έγγραφο και τίποτε άλλο από το σύστημα
- Η υπογραφή καταγράφει χρόνο, IP και δηλωθέντα υπογράφοντα, και ενημερώνει το `DpaContract` σε `SIGNED`
- Ληγμένο ή άγνωστο token δεν διαρρέει την ύπαρξη εγγράφου
- Το έργο δεν κλείνει όσο εκκρεμεί υπογραφή ή κρίσιμο κενό, και ο λόγος φαίνεται
- Με ορισμένη `SIGNATURE_TEST_RECIPIENT`, **κανένα** μήνυμα δεν φτάνει σε πραγματικό αντισυμβαλλόμενο, και αυτό αποδεικνύεται με δοκιμή
